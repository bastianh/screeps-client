TypeScript in the code editor

Write your bot modules in TypeScript directly in the client — with real IntelliSense, no build pipeline, and plain JavaScript deployed to the server.

What you get

  • Full IntelliSense in the browser: completion, hover type information, and inline diagnostics for the entire Screeps API — Game, Memory, room objects, and every game constant come from @types/screeps.
  • Per-module language: choose .ts or .js when creating a module. Branches can mix both freely.
  • Convert in place: a Convert to TS / Convert to JS button switches an existing module — including the protected main entry module.
  • Visible generated output: every TS module gets a read-only <name>.js (generated) entry showing the live transpiled JavaScript.
  • Type errors never block: diagnostics squiggle in the editor, but Save always works — exactly like a local ts-node-style workflow.

How it works in the browser

A real TypeScript language service runs inside a Web Worker, against a virtual file system that holds your branch's modules. The worker is lazily loaded: branches that only contain JavaScript never download the ~4.3 MB compiler chunk, and the main thread only ever talks to the worker through a thin message channel — typing stays smooth while the compiler churns in the background.

The TypeScript standard-library typings and @types/screeps are bundled offline with the client — nothing is fetched from a CDN. That means IntelliSense works everywhere the client runs, including embedded on a private server without internet access.

The language environment is tuned to the Screeps runtime:

  • Target ES2019, CommonJS modules, no DOM types — matching the server's isolated VM, so the editor won't suggest document or accept APIs the runtime doesn't have.
  • strict mode is on.
  • The runtime's ambient globals are declared: _ (lodash), require(), module.exports / exports, and global — so both idiomatic import/export and classic module.exports styles type-check.
  • Bare imports like import { x } from 'utils' resolve against your branch's flat module list, mirroring how Screeps' require('utils') works — sibling modules see each other's types from the first keystroke.

How your code is stored on the server

The Screeps server stores a branch as a flat name → source map of runnable JavaScript modules and has no notion of TypeScript. The client bridges that with a simple naming convention: a TypeScript module is persisted as two server keys.

In the editorOn the serverRole
main.ts main The compiled JavaScript — this is what the runtime actually requires and runs.
main.ts The original TypeScript source. Never required by the runtime, so it is completely inert — it just rides along in the branch.
utils.js utils A hand-written JS module maps straight to its key, as always.

When loading a branch, a runnable key with a matching <name>.ts sibling is recognized as the compiled artifact of a TS module and hidden from the module list — you edit the TypeScript, and the generated JS is shown read-only. A runnable key without a sibling is ordinary JavaScript.

Because everything lives in the branch itself, your TypeScript source survives reloads, other devices, and client updates — there is no local state to lose, and cloning a branch clones the sources with it.

⚠️ Two things to be aware of: other clients (including the official one) will show both main and main.ts as plain modules — don't edit the compiled main there, since the next save from this client regenerates it from the TypeScript source. And a hand-written JS module literally named foo.ts would be mistaken for TS source; the .ts suffix is reserved by convention.

What happens on save

  1. Every TypeScript module in the branch is transpiled to JavaScript in the worker.
  2. The branch is written back to the server: compiled JS under the runnable keys, TypeScript sources under their .ts keys.
  3. The server picks up the new code like any other commit — the runtime only ever sees plain JavaScript.

Transpilation is syntactic (types are stripped, not enforced): outstanding type errors are shown in the editor but never prevent deploying — you decide when a squiggle matters.

Bonus: the console uses it too

The console command line completes against the same in-browser TypeScript service — typing . or pressing Ctrl+Space on Game. offers the real API surface, ranked by your typed prefix. The worker loads on the first completion request, so sessions that never use it don't pay for it. Combined with the persistent per-server command history, the console feels like a small REPL.
